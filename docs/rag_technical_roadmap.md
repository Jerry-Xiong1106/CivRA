# CivRA RAG 技术路线（审查稿）

> 状态：供团队讨论与审查。本文聚焦法律知识库与检索模块，不预设最终模型、向量数据库或部署方案。

- 阶段 0 已有接口草案和 24 道检索开发题（21 题有参考依据、3 题超出语料）；接口协同确认、标注团队复核及最终测试集隔离仍待完成。
- 质量证据见 [数据质量报告](rag_data_quality_report.md) 和 [抽样复核记录](rag_review_notes.md)。开发题见 `evaluation/rag_retrieval_dev.jsonl`。
- 尚未实现 BM25、embedding 或向量索引；后续对比“仅正文”与“法律名称 + 章节路径 + 正文”，不固定将路径拼入向量输入。
- 当前保留 PDF 解析和基础校验两个功能脚本，以及回归测试、依赖文件。一次性审计脚本与辅助 JSON 已清理；`data/processed/` 仅保留三份最新法条 JSONL，评测题单独放在 `evaluation/`。

## 1. 目标与范围

RAG 模块为 CivRA 提供可复现、可评测、可追溯的法律资料检索能力，优先支持法规检索，并为后续司法解释、程序指引和相似案例检索预留扩展接口。检索结果应能回答“依据是什么、来自哪个版本、对应哪一条、何时有效”，而不是只返回相似文本。

项目演示场景以交通事故赔偿为起点，目标领域还包括合同、借贷、租赁和侵权赔偿。当前已有《中华人民共和国民法典》《中华人民共和国民事诉讼法》《中华人民共和国道路交通安全法》三份 PDF 及来源元数据。它们用于第一版端到端原型，不代表知识库已覆盖上述全部领域。

### 本模块负责

- 法律资料登记、解析、切分、元数据管理和索引构建/更新。
- 法规检索（首版），关键词与向量混合召回、结果融合和必要的重排。
- 返回原文、来源、条款定位、版本及效力信息。
- 检索评测样例与模块级测试，记录可复现的索引和检索配置。

### 本模块不负责

- Agent 主循环、动态工具调度和会话状态管理。
- 案件事实认定、证据冲突分析、法律意见或文书生成。
- 在缺少评测数据前训练专用 reranker、LoRA 或其他法律模型。

## 2. 设计原则

1. **条文优先，来源可追溯：** 以完整法条为基本检索单元，保留法条层级路径和原文定位。
2. **时间与版本是一等字段：** 允许按案件事实发生时间筛选或提示版本适用问题；不把最新版本自动等同于任意历史案件的适用版本。
3. **先建立基线，再增加复杂度：** 从确定性解析、BM25/关键词与向量混合检索开始，依照测试错误决定是否加入 query rewrite、多轮检索或学习式重排。
4. **不把相关性分数当法律结论：** 分数只用于排序。适用性仍需结合事实、时间和规范条件判断。
5. **无依据时允许不命中：** 返回空结果或不确定状态，不以低相关内容填满结果列表。
6. **索引可重建、变更可审计：** 原始资料、结构化文本和索引分层保存；记录构建配置与输入版本。

## 3. 分阶段实施

### 阶段 0：确定接口和资料基线

**工作内容**

- 核对三份 PDF 的来源、版本、生效状态和文件完整性；把已有 `legal_sources.json` 作为来源登记起点。
- 约定首版演示范围、资料允许来源、历史案件按哪个日期检索，以及索引产物是否提交 Git。
- 定义统一的法律文档/法条数据结构和 `search_statutes` 工具输入输出。
- 建立少量人工核验的检索问题和目标法条，后续作为回归集。

**交付物**

- 数据字段说明、资料清单和首版范围说明。
- 检索工具 JSON 契约草案。
- 初始检索评测集（建议先做 20–40 个问题，之后按覆盖和标注能力调整）。

**完成标准**

- 每份资料都能追溯来源和版本；接口使用方对必要字段达成一致。
- 评测问题有参考法条，包含至少一类应当无结果/信息不足的题目。

### 阶段 1：法规解析与条文级数据集

**工作内容**

- 以 **PyMuPDF（`pymupdf`）作为首版固定解析器**，按页提取文本和页码，检查页眉页脚、断行、乱码、条号遗漏和目录混入情况。当前先不维护多解析器抽象。
- 当前先处理有文本层的 PDF；只有发现扫描页或文本层不可用时，才为对应页面接入 OCR，并保留 OCR 来源标记。
- 解析法律层级：法律名称、编、分编、章、节、条及独立附则；条文无法可靠自动解析时明确报错并复核。
- 以“条”为基本 chunk，保持条文原文完整，并附层级路径。特别长的条文可在保留原条文 ID 的前提下切成子块，同时支持返回完整条文。
- 结构化存储原文和元数据；初始字段建议见第 4 节。
- 对 PDF 文本抽取结果做抽样核对，避免仅凭解析成功就入库。

**首版实现**

`scripts/parse_legal_pdf.py` 直接使用 PyMuPDF，内部利用行坐标过滤页面边缘已识别的页眉页码、合并同一基线的标题碎片，同时保持 PDF 自身阅读顺序以处理双栏。之后按“编—分编—章—节—条”组织数据，单独处理附则；暂不引入多解析器抽象和 fallback。

保留 `text_raw` 作为移除版式噪声后、有换行的正文抽取记录；`text` 清理中文断行空格。两者都不是原始 PDF 的字节级复制，引用应能回查来源文件。解析异常直接报错，首版不再生成单独审计 JSON。

**交付物**

- 可重复运行的解析脚本。
- JSONL 或等价的规范化法条数据。
- 解析质量报告和人工复核清单。

**完成标准**

- 三份 PDF 可以从头构建结构化法条数据。
- 每条数据都能定位回来源文件及条号；抽样检查无明显条号错配或正文截断。
- 每页解析结果保留页码；能定位条文所在 PDF 页。

### 阶段 2：检索基线与可追溯结果

**工作内容**

- 实现关键词检索（如 BM25）和向量检索两条召回通道。
- 向量方案先抽象为可替换接口；BGE-M3 可作为候选 embedding。向量存储先依据团队部署和数据量选择，Milvus 是候选项，不作为业务代码的硬依赖。
- 使用 Reciprocal Rank Fusion（RRF）或其他简单、可解释的融合方式合并候选；保留各通道排名和分数用于诊断。
- 支持按资料类型、法律名称、效力状态和案件时间等元数据过滤。
- 实现命令行/脚本入口，能独立构建索引并执行查询。

**首版检索流程**

```text
问题与可选过滤条件
  → 查询规范化（不改变实体、时间和否定条件）
  → 关键词召回 + 向量召回
  → 候选融合与去重
  → 元数据/时间过滤
  → 返回条文、来源与诊断信息
```

**交付物**

- 可重建的索引构建脚本和检索模块。
- 固定配置下可重复的查询结果。
- 每条结果包含原文、法律名称、条号、层级路径、来源、版本/效力和检索诊断字段。

**完成标准**

- 能以自然语言问题召回目标法条，并可切换关键词、向量、混合检索做对照。
- 能限制法律版本/效力条件；无合适结果时返回空结果，而不是伪造引用。

### 阶段 3：评测驱动的重排与检索增强

**工作内容**

- 与评测负责人共同标注查询对应的目标法条及可接受的相关条文。
- 统计 Recall@k、MRR/nDCG 等排序指标；人工抽查条文完整性、版本匹配、来源定位和无结果表现。
- 基于错误类型逐步试验：查询改写、多争点拆解、多 query 召回、RRF 参数、cross-encoder reranker。
- 重排特征可组合语义相关性、关键词命中、条款路径、法律类型、有效时间及明确规则；所有过滤规则和重排特征需可解释、可关闭、可比较。
- 多 query 结果保留 query 来源，合并时按法条 ID 去重，避免只因多次命中而虚增相关性。

**升级门槛**

- 只有当基线在固定评测集上暴露稳定且可归因的失败类型，才引入更复杂的改写、reranker 或模型训练。
- 任何优化都与原基线在同一语料、同一测试集、同一 top-k 下比较，并记录成本和延迟。

**交付物**

- 检索评测脚本、指标报告和失败案例。
- 基线与改进方案对照结果，以及保留/不采用某项技术的依据。

### 阶段 4：增量更新与版本检索

**工作内容**

- 为来源文档及规范化法条计算内容哈希（如 SHA-256），对比版本变化。
- 仅对新增或变更的法条重新生成向量和索引记录；删除或废止时保留审计信息，并更新检索状态。
- 支持同一法条多版本并存，以发布日期、生效日期、失效日期和来源版本区分。
- 按案件事实发生时间筛选候选版本；遇到过渡规定、追溯适用等复杂情形时返回版本信息供 Agent 进一步分析，不由检索层单独裁定法律结论。
- 记录索引构建时间、解析器/embedding 版本、语料哈希和配置，保证重建和回滚。

**完成标准**

- 同一份资料重复构建不会产生重复记录。
- 更新一份资料只影响对应文档/法条；历史版本仍可查询。

### 阶段 5：Agent 集成与稳定化

**工作内容**

- 将检索封装为 Agent 可调用工具，检索逻辑不依赖具体 Agent 框架。
- 支持按争点、法律类型和案件时间检索；多轮检索由 Agent 决定是否触发，RAG 返回足够诊断信息供其判断。
- 增加超时、空查询、过滤无效、索引缺失等错误处理；错误结构稳定且不泄露内部异常细节。
- 固定依赖和配置说明，准备从空环境构建语料/索引及运行检索的说明。

**交付物**

- 稳定的法规检索工具和调用示例。
- 安装、数据准备、索引构建、测试和已知限制说明。

## 4. 建议的数据结构与工具契约

### 4.1 法条记录（建议字段）

| 字段 | 含义 |
|---|---|
| `provision_id` | 稳定 ID；建议由来源标识、版本和条号组合或哈希生成 |
| `law_id` / `law_title` | 法律标识与名称 |
| `article_no` | 条号，保留原始格式 |
| `hierarchy_path` | 编、分编、章、节等父级路径；条号单独存储 |
| `text` | 规范化条文正文（清理版式空格，不做语义改写） |
| `text_raw` | 去除版式噪声后保留抽取换行的正文；原 PDF 为引用回查依据 |
| `source_url` / `source_file` | 官方来源链接和本地来源文件 |
| `publication_date` | 公布日期 |
| `effective_date` / `expiry_date` | 生效及失效日期；未知时为空，不猜测 |
| `status` | 资料登记的效力状态及核验状态 |
| `version_id` / `content_hash` | 版本标识和内容哈希 |
| `retrieved_at` | 获取日期 |
| `page_start` / `page_end` | 原始 PDF 页码（可获得时） |

### 4.2 `search_statutes` 输入草案

```json
{
  "query": "交通事故中机动车一方的赔偿责任如何确定？",
  "issue": "交通事故责任",
  "as_of_date": "2024-03-01",
  "law_types": ["法律", "司法解释"],
  "law_ids": [],
  "top_k": 8
}
```

`issue`、`law_types`、`law_ids` 可选。`as_of_date` 表示用于筛选候选规范的案件/事件日期；具体是否覆盖过渡规则需由上层推理处理。

### 4.3 返回结果草案

```json
{
  "status": "ok",
  "query": "交通事故中机动车一方的赔偿责任如何确定？",
  "results": [
    {
      "provision_id": "...",
      "law_title": "中华人民共和国道路交通安全法",
      "article_no": "第七十六条",
      "hierarchy_path": ["第五章 交通事故处理"],
      "text": "...",
      "source": {
        "url": "https://...",
        "file": "...pdf",
        "page_start": 8,
        "page_end": 8
      },
      "version": {
        "publication_date": "...",
        "effective_date": "...",
        "expiry_date": null,
        "status": "有效"
      },
      "retrieval": {
        "rank": 1,
        "score": 0.0,
        "matched_by": ["keyword", "vector"]
      }
    }
  ],
  "warnings": []
}
```

无命中时 `status` 可为 `no_results`，`results` 为空并给出必要提示。系统异常使用 `error` 状态及稳定错误码。分数是诊断用途，不应解释为法律适用概率。

## 5. 初始评测方案

首轮建议建立 20–40 个可人工核验的问题，覆盖：

- 明确法条/关键词查询与自然语言表达。
- 交通事故演示问题及民法典、民事诉讼法基础问题。
- 多争点问题（先拆成子问题评测，再测试合并）。
- 不同案件时间下的版本过滤。
- 语料没有充分依据或信息不足的问题。

主要检索指标：Recall@k（目标法条是否进入候选）、MRR/nDCG（目标条文排序）、版本/时间过滤准确性、来源定位准确率、条文完整率、无依据查询的拒答/空结果正确率。每项优化记录数据集版本、索引配置、embedding/reranker 版本、top-k、运行时间及失败案例。

## 6. 候选技术与采用顺序

| 能力 | 首版建议 | 后续候选 | 采用依据 |
|---|---|---|---|
| PDF 解析 | PyMuPDF 文本提取 | 扫描页确有需要时再接 OCR | 文本完整性、条号识别、版面噪声和定位准确性 |
| 切分 | 条文级，保留层级与完整原文 | 长条父子块 | 召回与上下文完整性测试 |
| 关键词检索 | BM25 | 法律同义词/术语扩展 | 关键词基线表现 |
| 向量检索 | embedding 接口可替换；BGE-M3 候选 | 其他中文/法律领域模型 | 固定测试集对比 |
| 向量存储 | 先选团队能稳定运行的方案 | Milvus | 数据规模、并发和部署需求 |
| 候选融合 | RRF 等简单方法 | 学习式融合/动态重排 | 可复现的排序增益 |
| Query 扩展 | 原查询为默认基线 | Query Rewrite、要素抽取、多 query | 复杂问题召回错误 |
| 生成/微调 | 不属于 RAG 首版 | Contrastive-CoT、LoRA | 系统级评测和数据条件成熟后再评估 |

## 7. 需要协作确认的事项

1. 首版演示的案由范围，以及第一批新增法律/司法解释的优先级。
2. 案件时间字段的语义、允许的日期过滤规则和过渡适用问题如何上交 Agent。
3. RAG 工具的 JSON 字段、空结果/不确定/异常状态及引用展示需求。
4. 评测集由谁维护、目标法条由谁复核、最终测试语料如何避免泄漏。
5. embedding、向量库、reranker 的部署资源和索引产物存放策略。
6. 法律资料许可/来源核验、更新责任人和版本发布流程。

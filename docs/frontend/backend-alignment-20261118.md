## 一、保持的界面

保留现有侧栏、案情沟通、案情图谱、对话卡片与工作面板。法律依据、处理路径、证据材料、结果分析、起诉状草稿仍在对话中展开。参考案例仍只在结果分析和案情图谱出现。CSS 与视觉布局未改。

主要变化在数据来源：新建案件走后端，旧本地记录和完整演示保留。旧数据不自动上传、不覆盖。工作面板提示文字调整为真实接口能力，未提供的数据不编造。

## 二、本轮已完成的前端适配

| 功能 | 接入方式 | 当前边界 |
| --- | --- | --- |
| 案件与聊天 | 创建/读取 conversation、messages、CaseSnapshot | 侧栏索引仍在本地；后端没有列表接口 |
| 连续对话与追问 | RunInfo、wait_id、reply.text，恢复同一 run | 等待中不能把新问题并行启动为另一轮 |
| 三路线选择 | 服务器菜单中的 route_choice | 无菜单时只请求评估意向，不在浏览器直接改阶段 |
| 运行进度 | fetch SSE、seq 游标、断线重连及状态刷新 | 后端当前返回步骤进度与最终回答，不逐 token 推正文 |
| 文件上传 | multipart 上传，附 file_id/file_version 提交解析请求 | 文件成功上传不等于 OCR、事实确认或检查完成 |
| 事实核对 | 读取真实事实及确认状态；修改/确认作为用户消息提交 | 没有绕过 update_case 写入本地伪确认；精确字段动作仍待专门接口 |
| 法律来源 | final.source_refs/citations → 原卡片 | 原文全文及全部检索候选尚未由 HTTP 提供 |
| 工作流/文书/成果 | outputs 与 structured_data → 原面板 | 只展示实际返回成果，不伪造工具执行 |
| 下载 | artifact_id → 受会话约束的下载接口 | 原表填写导出和普通草稿导出是不同链路 |
| 当前案情图谱 | 返回的日期事实、时间线成果、主张和证据 ID 对应 | 未生成日期或证据关联不补造 |
| 异常恢复 | request_id 幂等、409 刷新、401 提示、上传限额与类型、案件隔离 | 多用户鉴权范围未扩大 |

重要：服务器成果目录是按 output_id 排序，不是时间顺序。前端根据案情版本和消息里的成果引用顺序选择展示，避免把字典序当成新旧顺序。

## 三、要实现完整目标，仍需完成什么

### P0：把现有真实后端运行起来并联合验收

负责人：运行环境由成员四/负责部署的同学处理，成员二提供检索索引，成员三提供 OCR 环境，成员一/五联调。

- 安装仓库当前 Python 依赖，准备模型、embedding 与 RAG 索引。
- 后端设置 CIVRA_API_TOKEN；前端 Vite 代理使用相同工作区令牌。
- 运行 backend.api.app:app，默认 127.0.0.1:8000。
- 用实际模型走一轮：咨询→补充事实→上传材料→追问→路线确认→草稿→下载→重启恢复。
- 以实际模型和 OCR 的结果验收；脚本模型、前端测试和接口样本只能证明协议与交互。

本轮没有读取或生成模型密钥，没有运行付费模型调用；本机核对时未发现该工作树的实际后端配置，8000 端口没有服务。

### P1：完整工具结果与法律原文的数据通道

负责人：成员四提供运行结果，成员一维护 HTTP 与前端适配；成员二/三确认业务结构。

现状：

- GET 会话返回最终 source_refs 和已保存 outputs。
- search_statutes 的完整 matches / 原文保存在工具结果中，HTTP 没有公开读取端点。
- check_evidence 返回业务结果，但自身不持久化为 outputs；parse_documents 的分段结果也不能靠上传回执获取。
- SSE 的步骤结束事件不是完整业务结果。

需要补：

- 提供按 conversation/run/step 范围授权的只读工具结果端点，或把允许展示的结果持久化为有版本的业务成果。
- 返回 operation、status、case_version、output_ref、结构化 data、来源与定位。
- 前端按已知类型映射，不接收模型生成的任意 HTML。
- 这样才能在法条卡片显示真实原文，在材料卡片显示逐项重复、缺口、冲突与对应页码；没有结果不能显示检查通过。

### P1：协商、调解的可保存业务成果

负责人：**成员三**，成员四接调用，成员一接成果。

现有 compare_routes/get_route_workflow 可以给出路线条件与步骤；LLM 也能在对话中整理准备内容。但“协商提纲”“调解材料包”的版本化保存与导出不等于普通聊天文字。

需要定义：

- 协商提纲：已知事实、争议金额依据、沟通目标、待核验事项、用户给定可接受安排。
- 调解准备：拟用渠道与待核验条件、参与意愿、事实摘要、诉求、材料目录和缺失说明。
- 成果保存、案情版本、更新后的过期提示、导出和用户核对。
- 不自动承诺让步、不生成“已达成协议”或“已受理调解”的事实。

### P1：处理方向与实际程序阶段分开

负责人：**成员三**定义字段，成员四维护状态规则，成员一接 UI。

当前 CaseSnapshot.stage 为 consultation/route_selection/negotiation/mediation/litigation/closed，active stage 要与 selected_route 一致。它不是“已立案/已开庭/已判决”的程序阶段。

需要统一：

- 明确的 procedural_status 字段或约定一致、可追溯的程序事实。
- 来源、确认时间、陈述引用、变化历史，以及未知/有争议状态。
- 用于起诉状、调解渠道和执行条件的校验。

前端本轮不根据“选择调解”推断“尚未开庭”，也不根据“诉讼准备”推断“已经立案”。缺少专用协议时显示“程序阶段待确认”。
